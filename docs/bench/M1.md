# Bench log — M1

Same bench as [M0](M0.md): RetroScaler GBS-C on COM9, VGA→MS9288A→HDMI into an NZXT Signal HD60,
captured with `tools/bench/capture.py`. Source for every run below: RGB input, NTSC 15 kHz, composite
sync, 60.098 Hz field rate, a still game-selection menu. Run folders are under `bench-runs/`
(not versioned); the numbers quoted here are copied from their `result.json` or the console.

## 2026-10-13 — first picture from the new engine

| Item | Value |
|---|---|
| Detection | NTSC 15 kHz on RGB, composite sync, one program load |
| 960p (`ntsc-960p`, 162 MHz program) | the source needed 162.72 MHz, above the DAC rating; the line was shortened and the Si5351 locked at 161,639,599 Hz (`20261013-184741-m1-960p-locked`) |
| 1080p (`ntsc-1080p`) | Si5351 locked at 108,402,237 Hz, output = source rate (`20261013-184819-m1-1080p`) |
| Main loop | longest engine tick 303 ms (during detection; target 250 ms), free heap 49.7 KB without Wi-Fi |

The original firmware locks the same 1080p program at 107,999,272 Hz because it first shortens the
line to `VDS_HSYNC_RST` 1595; GBS Reimagined keeps the program's 1601 and moves the clock instead
(1601 / 1595 × 108.0 MHz = 108.41 MHz). Both give a 60.098 Hz output.

## 2026-10-13 — picture levels against the original firmware

**Symptom.** At 1080p our picture was brighter and less saturated than the original firmware's on
the same source: median luma 117.4 against 93.6.

**Register diff.** The original firmware's registers were read with its serial `d` command
(`bench-runs/ref-fw-dump.txt`) and ours with `dump 0`…`dump 5` (`bench-runs/ours-1080p-dump.txt`),
both at 1080p, and compared with `tools/bench/chip_diff.py`: 496 registers in both, 21 differ.
Besides the OSD block (the original has an on-screen menu; ours reads the chip's power-on values
with the OSD display off), the line-length trim above and the sampling phase, the differences are
all in the ADC front end:

| Field | Original | Ours |
|---|---|---|
| `ADC_RGCTRL/GGCTRL/BGCTRL` (gain; higher = less gain) | 0xD2 | 0x7B |
| `ADC_ROFCTRL/GOFCTRL/BOFCTRL` (black level) | 0x3E / 0x3D / 0x3D | 0x40 |
| `DEC_TEST_ENABLE` (decimator test output, used by auto-gain) | 1 | 0 |

**Experiment.** The original's six ADC values were written into ours on the live board
(`reg …`) and captured (`20261013-190112-ours-1080p-refadc`). Luma percentiles from 5 frames each:

| Run | p1 | p50 | p95 | p99.9 | mean saturation | mean R / G / B |
|---|---|---|---|---|---|---|
| original firmware (`…185153-ref-fw-1080p-again`) | 5.0 | 93.6 | 191.5 | 213.4 | 84.2 | 87.9 / 119.1 / 136.9 |
| ours, gain 0x7B, offsets 0x40 (`…184819-m1-1080p`) | 6.0 | 117.4 | 210.1 | 218.7 | 99.3 | 100.3 / 140.5 / 170.5 |
| ours with the original's ADC values | 5.0 | 93.9 | 190.9 | 213.1 | 84.0 | 87.9 / 119.0 / 137.0 |

With equal ADC values the pictures match within capture noise: the scaling, colour and output
stages agree, and the whole difference is the ADC gain.

**Gain sweep** (offsets 0x3E/0x3D/0x3D; runs `…-gain-0x7B` to `…-gain-0xD2`):

| Gain | p50 | p99 | p99.9 | share of red pixels at 214–218 |
|---|---|---|---|---|
| 0x7B | 118.9 | 217.0 | 219.0 | 6.03 % |
| 0x90 | 112.0 | 217.0 | 218.6 | 5.39 % |
| 0xA0 | 105.0 | 217.0 | 218.2 | 4.84 % |
| 0xB4 | 101.0 | 216.3 | 218.2 | 3.33 % |
| 0xD2 | 93.9 | 208.4 | 212.9 | 0.01 % (the red plateau sits at 196–204) |

The output chain tops out near 218 (M0). At the preset gain 0x7B this source's whites pile up there;
the pile shrinks with less gain and is gone at 0xD2. The original firmware had `DEC_TEST_ENABLE` on
and gains far from any preset value, i.e. its auto-gain was active. The ADC's own reading (below)
shows that 0xD2 is about where this source's green stops clipping, which is where that loop stops.

### Reading the ADC levels

The levels were then read from the chip itself, through the decimator's test output
(`TEST_BUS_SEL` 0x0B, `DEC_TEST_ENABLE` 1, `DEC_TEST_SEL` picks the channel; console `levels`).
Findings, each from 1500–4000 reads of `TEST_BUS_2F` on the menu at 1080p:

- **Bit 7 of `TEST_BUS_2F` is a flag, not data.** Every level appears twice in a histogram, as *v*
  and *v* + 0x80, in roughly equal numbers. The level is bits 0–6; 0x7F is the ADC's ceiling. The
  community firmware's auto-gain tests `TEST_BUS_2F == 0x7F` and so misses the half of the clipped
  samples that carry the flag.
- **`DEC_TEST_SEL` 1 is green and 2 is red,** read directly: lowering one channel's gain register
  moves only that selector's levels, with the decimator matrix on or bypassed.
- **`DEC_TEST_SEL` 3 is blue only with `DEC_MATRIX_BYPS` = 1.** With the matrix on (as RGB programs
  leave it, S5_1F = 0x90) it reads a colour difference centred on 0x40: black and blanking at
  0x40, the blue background above, yellow text below, and it shifts when the red gain changes.
  Bypassed, it reads blue from 0 (blue background at 0x74–0x75 at gain 0x7B).
- **Gain response.** The plateau of a uniform area follows level ∝ 1 / (199 + gain register):
  green 0x49 → 0x39 from 0x7B to 0xD2 (model 1.27, measured 1.28), red 0x27 → 0x1E (1.27 / 1.30),
  green 0x37 at 0xE0 (model 0x37). The register therefore spans about 0.71× (0xFF) to 1.30× (0x30)
  of the preset gain.

Share of reads at the ceiling against the gain register:

| Gain | Red | Green |
|---|---|---|
| 0x7B | 9.60 % | 7.63 % |
| 0x90 | 8.27 % | 6.90 % |
| 0xA8 | 5.90 % | 5.97 % |
| 0xB8 | 0.83 % | 4.97 % |
| 0xC4 | 0.00 % | 3.90 % |
| 0xD2 | 0.03 % | 0.17 % |
| 0xE0 | 0.03 % | 0.07 % |

Blue, read with the matrix bypassed, clips on 6.0 % of reads at 0x7B. All three channels clip on
this source at the preset gain.

**Offset calibration.** GBS Reimagined now calibrates the three black levels at every bring-up
(`video/adc_levels.cpp`). On this board it lands on 0x3E / 0x3D / 0x3D, the same values the original
firmware found; black (p1) stays at 5–6 either way (`20261013-191204-m1-1080p-offsetcal`).

**Auto gain (`input.autoGain`).** With the setting on, the gains went from 0x7B to 0xD1 within 20 s
of switching it on and stayed there for the next two minutes. The capture then matches the original
firmware within noise (`20261013-201501-m1-1080p-autogain`):

| Run | p1 | p50 | p95 | p99.9 | mean saturation | mean R / G / B |
|---|---|---|---|---|---|---|
| original firmware | 5.0 | 93.6 | 191.5 | 213.4 | 84.2 | 87.9 / 119.1 / 136.9 |
| GBS Reimagined, auto gain | 5.0 | 93.9 | 190.9 | 213.6 | 84.1 | 87.9 / 119.1 / 137.0 |

**Calibrate levels.** Started on the menu (no large white area), it ended "not white" and left the
gains unchanged, as intended. A run on a white screen is still to be recorded.

**Consequence for the M1 gate.** The M0 baseline capture was taken with the original's auto-gain
active, so picture levels are compared with auto gain on (or at equal ADC gain); geometry,
sharpness, lock and stability are compared directly.

## 2026-10-13 — Wi-Fi, web UI and API

**Setup access point.** With no saved network the board opened `GBS-EAC4` (WPA2, `qqqqqqqq`); a
phone joined it and the captive portal showed the UI.

**Page delivery.** The first build served the 20 KB gzip page with the core's `send_P`, and the
phone's browser reported `ERR_CONTENT_LENGTH_MISMATCH` with a black page: the core streams flash
data through a small buffer and stops at the first partial write, which the low-memory TCP stack
produces. Writing the page in 512-byte blocks and resuming partial writes fixed it; from the PC the
page now arrives whole (20 330 of 20 330 bytes in 0.49 s) and a repeat with the ETag answers 304.

**Joining the home network.** The first join appeared to work but had not: the password had been
mistyped on the phone, and while the phone stayed on the board's own network the captive DNS
answered `gbs.local` with the board, so the UI kept opening. The console log then showed every
attempt refused (`status 6` = wrong password, SDK reason 15 = 4-way handshake timeout) on both
access points of the network (a mesh: -20 dBm and -60 dBm, channel 6, WPA2-CCMP). With the
password typed again the board joined through the -20 dBm node (RSSI -28 dBm in use) at
10.0.0.119; `gbs.local` resolves from Windows. Since then a failed join is reported on the setup
page ("the network refused the password", "not found", "no answer"), and each access point of the
network is tried in turn.

**API from the PC** (curl, board joined): `/api/status` and `/api/settings` as specified;
`POST /api/settings` reports per-setting outcomes (`applied`, `invalid` for an out-of-range value);
a POST with a foreign `Origin` is refused with 403. A risky change (`output.resolution` r1080p →
r960p) answered `revertArmed`, the status counted 19 → 1 s, and the board went back to r1080p at
20 s on its own.

**Heap (B-03, idle part).** Joined, one client polling `/api/status` every 1.5 s for 25 s: free
heap 38 112–39 032 B, low-water mark since boot 35 544 B (budget ≥ 24 KB,
[memory-budget.md](../design/memory-budget.md)). The OTA half of B-03 waits for M3.

## 2026-10-13 — OLED, knob and safe mode

Checked by the user on the board: the splash, the home screen (headline, source, output clock,
address), the menu and value editing, live brightness while turning, and a long press backing a
change out. The knob first ran backwards: with A on GPIO14 and B on GPIO13 a clockwise turn counts
negative, now recorded in the board profile (`encoderClockwiseNegative`). Holding the knob for five
seconds during the splash started safe mode (defaults, 480p, "SAFE MODE" on the home screen); the
next normal start brought the saved settings back.
