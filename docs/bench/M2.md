# Bench log — M2

Same bench as [M1](M1.md): RetroScaler GBS-C on COM9, VGA→MS9288A→HDMI into an NZXT Signal HD60,
captured with `tools/bench/capture.py` (BT.709 matrix). Run folders are under `bench-runs/` (not
versioned); the numbers quoted here are copied from them or from the console.

## 2026-10-14 — What the converter shows

The geometry settings need to know how much of each output line ends up on the screen. The answer
came from the M1 output-matrix captures, re-analysed.

**Method.** `tools/bench/picture_extent.py` measured the picture's bounding box in each run's first
frame (rows and columns with more than 20 pixels above level 40). The HD60 delivers every mode as
1920 × 1080, so the picture width in capture pixels is a share of whatever the converter treats as
the active line. That share was converted into the source's active time:

`active µs = width_px / 1920 × visible × hscale / 1024 / IF_line × line_period`

- `visible = (VDS_HSYNC_RST + 1) × active / total` of the standard timing the converter recognises
  (the hypothesis being tested);
- `hscale` and `IF_line` (`IF_HSYNC_RST + 1`, samples per source line) are the program's own
  values (`schema/programs/`; hscale 1024 = the scaler bypassed);
- `line_period` is 63.556 µs for NTSC and 64 µs for PAL.

| Run (`bench-runs/…`) | Program | Line | IF line | hscale | Converter timing (active / total) | Visible units | Picture px | Active µs |
|---|---|---:|---:|---:|---|---:|---:|---:|
| `20261013-233443-240p-1080p` | ntsc-1080p | 1602 | 1280 | 1024 | 1920 / 2200 (CEA-861 1080p) | 1398 | 1318 | 47.65 |
| `20261013-233346-240p-960p` | ntsc-960p | 2705 | 1173 | 512 | 1280 / 1800 (VESA 1280×960) | 1924 | 1760 | 47.77 |
| `20261013-233414-240p-1024p` | ntsc-1024p | 2536 | 1173 | 512 | 1280 / 1688 (VESA 1280×1024) | 1923 | 1756 | 47.65 |
| `20261013-233512-240p-720p` | ntsc-720p | 2403 | 1173 | 512 | 1280 / 1650 (CEA-861 720p) | 1864 | 1812 | 47.66 |
| `20261013-233540-240p-480p` | ntsc-480p | 2574 | 1173 | 512 | 640 / 800 (VESA 640×480) | 2059 | 1640 | 47.65 |
| `20261013-232633-576i-ps2-1080p` | pal-1080p | 1445 | 1277 | 1024 | 1920 / 2200 | 1261 | 1397 | 45.99 |
| `20261013-232536-576i-ps2-960p` | pal-960p | 2167 | 1135 | 607 | 1280 / 1800 | 1541 | 1715 | 46.01 |
| `20261013-232605-576i-ps2-1024p` | pal-1024p | 2033 | 1135 | 585 | 1280 / 1688 | 1542 | 1777 | 45.96 |
| `20261013-232702-576i-ps2-720p` | pal-720p | 2166 | 1171 | 626 | 1280 / 1650 | 1680 | 1572 | 45.97 |

The NTSC source was a Mega Drive in H40 mode. Its documented figures — 320 pixels at the 53.693 MHz
master clock divided by 8, i.e. 47.68 µs — are not measured here, but four of the five NTSC rows
land within 0.1 % of them. The 960p row reads 0.25 % above the others. That program's line is
shortened at run time for the clock limit (M1, first picture), which the table does not account
for; how much it was shortened in this run is not recorded, so the cause is unconfirmed. The
1080p program keeps its own line: on 2026-10-14 the board reported the window 348..1356 at
107.97 MHz with the same console, as in the matrix run. The PAL source (a PS2 at 576i) comes out
at 45.96–46.01 µs on all four programs **with the 60 Hz shares**: the converter shows the same
share of the line at 50 Hz.

**Conclusions.**

- The converter shows a fixed share of each output line: the active share of the standard timing
  it recognises for that mode. `video/geometry.cpp` uses these shares.
- PAL 576p (`pal-576p`, run `20261013-232730-576i-ps2-480p`) fits no standard timing: with the
  PS2's 45.98 µs, its 1593-px picture gives a share of 0.781, which the code uses. That capture was
  also cut vertically (rows 0–960), so this value was inferred from one run; the PAL run below
  confirms it.
- The same numbers give each program's aspect, taking BT.601's 4:3 width (704 samples at 13.5 MHz =
  52.148 µs) over the source's full height (480 or 576 lines after the line doubler). These are
  predictions from the model, to be confirmed on the bench:

  | Program | Horizontal scale for 4:3 | Program's own | Shape as loaded |
  |---|---:|---:|---|
  | ntsc-1080p | 1024 (1:1) | 1:1 | 4:3 (0.15 % wide) |
  | ntsc-960p | 512 | 512 | 4:3 |
  | ntsc-720p | 705 | 512 | 38 % wide (fills the 16:9 frame) |
  | ntsc-1024p | 512 at 960 lines | 512 at 1013 lines | 5.6 % tall |
  | ntsc-480p | 478 | 512 | 7 % narrow |
  | pal-1080p | 1126 | 1:1 | 10 % wide; out of reach (see below) |
  | pal-960p | 615 | 607 | 1.3 % wide |
  | pal-720p | 775 | 626 | 24 % wide |
  | pal-576p | 482 | 512 | 6 % narrow (inferred share) |

- **PAL at 1080p cannot be made 4:3 by the scaler.** The scaler only enlarges horizontally (its
  divisor stops at 1:1), and the program already samples each line 10 % wider than 4:3 needs. A
  narrower picture would need a lower sampling rate (`PLLAD_MD`) for that program, which is not part
  of the geometry work. Horizontal size below 0 has no effect at 1080p for the same reason.

## 2026-10-14 — Geometry on the board

Source: the Mega Drive on the 240p Test Suite grid (RGB input, composite sync, NTSC 15 kHz,
VPERIOD_IF 523, 59.86 Hz). Every condition was set over the console, captured
(`bench-runs/20261014-12*` to `-14*`) and measured with `tools/bench/picture_extent.py`; rows that
break the grid's vertical structure were counted with a scratch detector (a row differing from both
neighbours where they agree). Widths are on the 1920-px capture.

**The shapes come out as predicted.**

| Output, aspect | Predicted | Measured |
|---|---:|---:|
| 1080p 4:3 (program unchanged) | 1318 × 1009 | 1317 × 1009 |
| 1080p 16:9 (divisor 769) | 1755 wide | 1754 |
| 720p 4:3 (705; the program filled the width) | 1317 wide | 1315 |
| 720p 16:9 | 1755 wide | 1756 |
| 1280x960 4:3 | as M1 | 1754 × 1010 |
| 1280x960 16:9 (letterbox, vertical 683) | 756 tall | 757 |
| 1280x1024 4:3 (letterbox to 960 lines) | 945 tall | 946 |
| 1280x1024 Full (vertical 480) | 1008 tall | 1010 |
| 480p 4:3 (478; the program was 7 % narrow) | 1756 wide | 1756 |

On every 4:3 or 5:4 output the 4:3 picture now measures 1754–1756 px, and on both 16:9 outputs
1315–1317 px (1756 × ¾ = 1317).

**Horizontal position: move the window, not the capture.** Starting the capture 20 samples earlier
moved the picture but brought a dark green, full-height band into the window's left edge: the
decoder's green from before the source's active line (videopath lessons §1.7). Moving the whole
window (display, fetch and mask) instead moved the picture 55 px per 40 output units at 1080p
(1.37 px per unit), with the width unchanged and nothing new at the edges.

**Vertical: the fetch blanking is the anchor.** Letterboxing by starting the capture 80 lines
earlier (wrapped into the previous frame) put the picture's top in the right place but lost its
bottom, and repeated its top below: the frame memory holds one frame from the capture start. Moving
`VDS_VB_ST/SP` down with the display window instead (24/26 → 145/147 at 1280x960, capture start
unchanged) letterboxed cleanly, 757 px against 756 predicted. `VDS_VB` therefore positions the
content the way `VDS_HB` does. Small wraps (6 and 20 lines) had worked, which is why the first
design looked right on 1280x1024.

**Horizontal divisors below 512 at 1280x960.** 489 displaced one line in one run out of four, 467
displaced several, 447 garbled the whole picture, with or without the capture crop; 514 never did.
480p's 4:3 runs at 478 with no defect. The geometry keeps the divisor at 512 or above unless the
shape itself needs less. In passing, `IF_HB_ST2` set past the input line (1187 > 1173) sheared the
picture diagonally; the reference calls it inert, which holds only inside the line, and the
geometry does not write it.

**The fetch length per line.** At some scales a thin, squashed copy of the picture (its rows and
border lines) appeared in the black border, 40–110 px from the picture: at the far left at 1080p
16:9, at the far right at 720p 4:3. Varying the fetch blanking by hand showed that the fetched
samples per line, `(VDS_HB_ST − VDS_HB_SP) × hscale / 1024`, decide it:

| Output | Fetched samples | Result |
|---|---:|---|
| 1080p 16:9 (769) | 1015, 1021 | clean |
| 1080p 16:9 | 1023, 1027, 1038 | stray column |
| 720p 4:3 (705) | 1011 | clean |
| 720p 4:3 | 1019, 1030 | stray column |

`PB_FETCH_NUM` reads 256 (1024 samples). Ending the fetch earlier (a longer fetch tail) removed the
column without moving the content, which is anchored at the fetch start. The geometry limits the
fetch to 1008 samples whenever the divisor differs from the program's own. A shorter lead removed
it too, but moves the content.

**Final run** (the committed geometry, each output freshly loaded with the aspect already set;
`bench-runs/20261014-14*-v-*`):

| Output | Aspect | Picture (px) | Stray columns | Broken rows |
|---|---|---|---|---|
| 1080p | 4:3 | 1318 × 1009 | none | 0 |
| 1080p | 16:9 | 1754 × 1009 | none | 0 |
| 720p | 4:3 | 1316 × 1009 | none | 0 |
| 720p | 16:9 | 1757 × 1009 | none | 0 |
| 1280x960 | 4:3 | 1754 × 1010 | none | 0 |
| 1280x960 | 16:9 | 1754 × 757 | none | 0 |
| 1280x1024 | 4:3 | 1756 × 946 | none | 0 |
| 1280x1024 | 16:9 | 1756 × 709 | none | 0 |
| 1280x1024 | Full | 1756 × 1010 | none | 0 |
| 480p | 4:3 | 1756 × 1009 | none | 0 |

Position (±20 steps horizontally, ±10 vertically at 1080p and 1280x960) and size (±20 at 1080p,
+30 vertically at 1280x960) were clean in the runs before it, with the picture cut where it crossed
the frame's edge.

**Other observations.**

- Scaling pivots on the program's window centre, which at 1080p sits about 51 px left of the frame
  centre (inferred from two zoom factors); the Mega Drive's picture is right-aligned in the program's
  capture, so widening moves it slightly right of where it was.
- The program's own capture start varied between loads by two input-formatter lines (one source
  line): M1's adjustment for 523-line sources keys on a single `VPERIOD_IF` read at load time.
  Not a geometry effect, left open.
- After a flash, booting straight into 1280x960 left the capture card black and then without
  frames; switching 1080p → 1280x960 worked every time. Not a geometry effect (position changes on
  1280x960 behaved), left open.

## 2026-10-14 — Geometry with a PAL source

Source: a PS2 at 576i on RGB (composite sync, VPERIOD_IF 624, deinterlacing), on a menu screen.
Each output was freshly loaded with the aspect already set (`bench-runs/20261014-151*-pal-*`); the
picture's full width is the span from its first to its last lit column (the menu has a wide dark
gap, so the extent is read by eye on each frame, not by the stray-column check).

| Output, aspect | Predicted width (px) | Measured |
|---|---:|---:|
| 1080p 4:3 (divisor held at 1:1) | 1397 | 1397 |
| 1080p 16:9 (845) | 1693 | 1692 |
| 720p 4:3 (775; the program was 24 % wide) | 1270 | 1270 |
| 720p 16:9 (581) | 1693 | 1693 |
| 1280x960 4:3 / 16:9 | 1693 | 1691 / 1692 (16:9 height × 0.751) |
| 1280x1024 4:3 / 16:9 / Full | 1693 | 1691 each (heights × 0.939 / 0.705 / 1, predicted 0.9375 / 0.703) |
| 576p 4:3 (482) | 1693 | 1693 |

- **The inferred 576p share (0.781) is right**: the PS2 comes out 1693 px wide as on every other
  4:3 frame.
- **PAL at 1080p is 10 % wider than 4:3, as predicted** (1397 against 1270 at 720p): the divisor
  stops at 1:1.
- **576p cut the top of the picture.** That program starts its capture at line 42 where the other
  PAL fits start at 18 (M1). Starting it at 18 shows the whole picture (top at row 5 instead of
  being cut); `fitPalVertical` now treats 576p like the others, keeping its 1:1 scale.
- Position on PAL at 1080p: +20 horizontal moved the picture 61 px (40 units × 1.53 px), +10 vertical
  38 px (3.75 output lines per source line, at divisor 546), −10 cut the top at the sync limit; no
  wrap, width unchanged.
- The broken-row check fired on 0–6 rows per capture here; the frames show no defect (the menu's
  thin interlaced text trips it).

## 2026-10-14 — Scanlines and deinterlacer

**Deinterlacer** (PS2 at 576i on RGB, a still menu, pal-1080p; `bench-runs/20261014-1657*-deint-*`).
Twelve frames per condition, two interleaved rounds. Vertical detail is the mean absolute
row-to-row difference; change is the mean absolute difference between consecutive frames.

| Mode | Vertical detail | Frame-to-frame change |
|---|---:|---:|
| Motion adaptive | 2.509, 2.513 | 0.673, 0.671 |
| Bob | 2.076, 2.074 | 2.850, 2.841 |

Bob loses 17 % of the vertical detail and shows 4.2× the frame-to-frame change on still content
(line twitter), the direction the reference measured (−12 %, 1.07 → 1.81). Turning scanlines on with
this interlaced source left them paused and the deinterlacer engaged.

**Scanlines** (Mega Drive, 240p Test Suite grid; brightness profile down the grid's white vertical
lines, rows 300–780 of the capture; `bench-runs/20261014-18*-scan-*`):

| Output | Level | Mean | Modulation at one source line | Rows over two source lines |
|---|---:|---:|---:|---|
| 1280x960 | off | 203.0 | 0.0 | flat |
| 1280x960 | 1 | 208.0 | 5.7 | 208 201 206 214 212 203 202 211 215 |
| 1280x960 | 4 | 168.3 | 54.0 | 169 103 154 229 205 124 114 196 233 |
| 1280x960 | 8 | 116.7 | 111.0 | 116 0 82 245 195 16 0 174 247 |
| 1080p | off | 201.3 | 0.0 | flat |
| 1080p | 4 | 170.2 | 45.4 | 122 123 208 208 208 122 122 208 208 |
| 1080p | 8 | 123.1 | 100.6 | 18 18 208 208 208 18 18 208 208 |

- Level 4 (the default) darkens the picture by 15–17 %, level 8 by 39–42 % with black gaps; level 1
  is barely visible and slightly brighter, from the white-level lift that comes with the mixer path.
- At 1280x960 (4×) the pattern is regular; the capture card's 960 → 1080 resampling blurs it into the
  9-row repeat above. At 1080p (4.5×) the dark lines are always two output lines and the bright ones
  alternate between three and two, as expected for a non-integer scale.
- Turning them off restored the picture exactly (203.0 and 201.2, flat).

**240p ↔ 480i with scanlines on** (the Test Suite's resolution switch, 1080p): at 480i the status
showed the deinterlacer engaged and no scanlines, the picture clean; back at 240p the scanlines came
back by themselves. No program reload either way (four loads before and after).

## 2026-10-14 — Sampling controls

Sources: the Mega Drive (RGB, composite sync from the sync input, 240p) and a Wii (component, sync
on Y, 480p), 1080p output. Quality read from the console three times per condition; edge sharpness
is the mean horizontal gradient over lit pixels of four captured frames.

**Sync threshold.**

| Source | SOG 0 | SOG 1–2 | SOG 2–31 |
|---|---|---|---|
| Mega Drive (sync input) | 100 % | 100 % | 100 % |
| Wii component (sync on Y) | 0 %, picture rolling and torn (frame-to-frame 9–32) | 100 %, clean (1.1) | 100 % |

- The Mega Drive's TTL composite sync does not pass the slicer the threshold sets: no level made a
  difference, and no sync-processor phase (0–28 by hand) disturbed it either.
- On the Wii, SOG 0 broke the picture while the line length still equalled the PLL divider (2558,
  2557 once in eight reads). The sync processor's line count per field jumped between 100 and 244
  instead of 524, and `VPERIOD_IF` between 982 and 1049 (eight reads each). The first meter read
  0 % through the latched SOG-bad flag; the firmware review showed that one glitch would pin it
  there, so the meter now counts a field count that holds still (rechecked below).

**The revised meter** (line length and a steady field count, no latched flag), rechecked on the
Wii: SOG Auto 100 %, 100 %, 100 %; SOG 0 0 %, 0 %, 5 %; SOG 1 100 %; back to Auto 100 %.

**ADC phase and filter.** The registers followed every setting (phase 0–28, filter 150/110/70/40
MHz) live, with no effect on sync, and Auto restored the automatic values (phase 0 on the 240p
program, 16 on 480p; filter 40 MHz). The effect on the picture stayed below this method's noise:
edge sharpness 15.6–15.8 on the Mega Drive (about eight samples per console pixel at 240p), 2.7–3.1
on the Wii menu, which animates.

## 2026-10-14 — Force 60 Hz

Source: the PS2 at 576i on RGB (`bench-runs/20261014-195*-f60*`, `-200*-f60b-*`, `-2003*-pal960-*`).

| Output | Force 60 Hz | Program | Clock | Output rate | Picture (px) |
|---|---|---|---|---|---|
| 1080p | off | pal-1080p | 81.35 MHz, locked | 49.78 Hz | 1397 × 1018 |
| 1080p | on | ntsc-1080p | 108 MHz internal | 59.87 Hz | 1269 × 1018 |
| 1280x960 | off | pal-960p | 108.45 MHz, locked | 49.79 Hz | picture |
| 1280x960 | on | ntsc-960p | 162 MHz internal | 59.83 Hz | 1692 × 1018 |

- The HDMI converter and the capture card took the forced 60 Hz output at both rates.
- All 576 lines show (the same 1018-px height as on the 50 Hz programs) once the vertical window
  holds at least the source's full height; the first build showed only the 482 lines the 60 Hz
  program captures (873 px).
- At 1080p the picture comes out at true 4:3 (1269 px, predicted 1270) instead of the 50 Hz
  program's 1397.
- Off → on → off at 1280x960 reloaded each time and locked again (three runs, plus once after a
  console reboot and once after a flash). Once, right after a flash, turning it off left pal-960p on
  the generator at 108.000 MHz unlocked, with an output measured at 99.58 Hz and no picture; that
  did not happen again. Right after a flash, opening the serial port resets the board once more,
  which is what made two other captures black.
- Judder was not measured: the menu on screen does not move.

**Auto-load across consoles.** Profile 1 "PS2 PAL" (1080p, signed for the PS2) and profile 3
"Mega Drive" (1280x960, signed for the Mega Drive, `rgb csync 240p/480i 260 lines`), both on RGB.
When the Mega Drive first arrived with only profile 1 signed, profile 1 stayed in use: it matches
on the port alone. The user then swapped consoles four times while the console `status` was polled
every 2 s:

| Time | Source | Program | Loads | Profile |
|---|---|---|---|---|
| 0 s | Mega Drive | ntsc-960p | 5 | 3 Mega Drive |
| 408 s | PS2 | pal-1080p | 7 | 1 PS2 PAL |
| 423 s | Mega Drive | ntsc-960p | 9 | 3 Mega Drive |
| 431 s | PS2 | pal-960p | 10 | 3 Mega Drive (not yet) |

  first loads the new console with the output in use, then the profile changes the output and the
  program loads again, within 2 s of the first (the poll interval; ADR 0014, consequences). With
  the same output in both profiles a swap costs one load.
- The OLED showed the `«` mark beside the profile in use (seen by the user).
