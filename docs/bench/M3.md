# Bench log — M3

Same bench as [M1](M1.md) and [M2](M2.md): RetroScaler GBS-C on COM9, joined to the home Wi-Fi,
VGA→MS9288A→HDMI into an NZXT Signal HD60. Numbers are copied from the serial console, `curl`
and the board's status.

## 2026-10-15 — Firmware update over the network (`/api/update`)

**Method.**
- Two builds of the same source: image A reporting `0.1.0-dev` and image B reporting
  `0.1.0-ota-test`, so the version shows which image runs.
- Each was turned into an update file with `tools/release/ota_image.py`: gzip with the comment
  `gbsr board=gbsc version=…`, 389 KB from 568 KB (68 %).
- Each file was sent with `curl -F file=@… http://<board>/api/update` from a computer on the same
  Wi-Fi, while the serial console logged the board's side.

**Refusals, before any flash write:**

| File | Answer |
|---|---|
| the full image (`firmware.bin`, 568 KB) | 400 `notGzip` |
| an update file naming another board | 400 `wrongBoard` |
| B, with `Sec-Fetch-Site: cross-site` | 403 `refused` |

Each was answered about 1 s after it was sent. With nothing to write, the board read the 389 KB
as fast as the network delivered them; curl had sent everything 0.75 s after the request.

**Updates.**
- A → B → A → B → A all installed. Each time the board came back running the version it was sent,
  and the picture came back (`scaling`).
- The saved profiles, the active profile and its *modified* mark, and the settings were kept every
  time.
- The serial log of one update reads:
  - `update: receiving 0.1.0-ota-test`
  - `update: 389061 bytes, ok, free heap low 24880`
  - the boot ROM
  - about 5 s while the bootloader copies the image
  - the new firmware's banner
- **B-03, free heap during an upload:** 24 880 and 26 912 bytes at the lowest, in the two updates
  whose console log was kept. The budget is 12 KB or more
  ([memory-budget.md](../design/memory-budget.md)). The reference project lost HTTP OTA below about
  15 KB ([platform lessons](../research/gbs-control-lessons-platform.md) P9, P11; reference project,
  not reproduced here).

**A fault found and fixed: the answer never arrived (the board restarted before sending it).**

- What was seen: every update took about 64 s, and the browser got no answer.
- What it was: the restart was scheduled at "start of the loop pass + 300 ms". The upload had kept
  that pass busy for seconds, so the board restarted at once, before its answer left. The 60 s was
  curl waiting until the connection reset.
- Fix: the restart is now scheduled from the moment it is asked for, 500 ms later. The OLED's
  *Restart* had the same flaw and got the same fix.
- With the fix an update takes **4.1 to 4.2 s** from start to answer: about 2.6 s to send and
  1.3 s to finish the flash. The bootloader's copy (about 5 s) and the boot follow; the picture
  was back (`scaling` in the status) **17.9 s** after the start of the upload.

**Wi-Fi power saving.** A first diagnosis blamed the modem's power saving for the slow updates; it
was the restart. An image that leaves power saving on took the same time (4.12, 4.13 and 4.14 s
over three updates), so the board does not touch it.

**After the firmware review:**

| Case | Result |
|---|---|
| a request with no file part | 400 `noFile` |
| an update cut off after 2 s at 50 KB/s (about a quarter sent) | nothing installed: the board kept the version it had, with the picture, and the next update installed normally (4.16 s) |

The core's web server parses a multipart upload one byte at a time. That is enough at about
150 KB/s (389 KB in 2.6 s), so a block reader was not needed. Its read has no deadline of its own:
a client that stops sending in the middle holds the main loop until the connection drops (not
tested; the picture runs on in the scaler meanwhile).

## 2026-10-15 — Browser installer and Improv Wi-Fi Serial

**Method.**
- Firmware `0.1.0-dev` with Improv, written over USB without erasing (settings, profiles and Wi-Fi
  kept); flash backed up first.
- The installer site built locally (`uv run tools/release/installer_site.py --build --version
  0.1.0-test`, then `pnpm -C installer serve`) and opened in Chrome on `http://localhost:4173`. The
  manifest named `0.1.0-test` so that ESP Web Tools 10.4.0 would offer an update of the running
  `0.1.0-dev`.
- `tools/board/board.py improv` asks what the installer asks (state, device information, networks)
  without a browser and never sends Wi-Fi settings.

**Improv without a browser** (`board.py improv --scan`, the board joined to the home Wi-Fi):

| Asked | Answer |
|---|---|
| current state | "no error", then `provisioned` and the result `http://10.0.0.119/`, 125 ms after asking |
| device information | `GBS Reimagined`, `0.1.0-dev`, `ESP8266`, `GBS-EAC4` |
| networks | one network heard (its name is not recorded here), then the empty result that ends the list, 1.7 s after asking |

The console kept answering (`status`) after the Improv traffic.

**In Chrome, by the user** — every step worked as expected:
1. The page opened in Portuguese and the language buttons switched it.
2. *Install*, port USB-SERIAL CH340 (COM9): the dialog showed the board, `GBS-EAC4`, running
   `GBS Reimagined 0.1.0-dev (ESP8266)`, with *Update GBS Reimagined*, *Visit Device*, *Change
   Wi-Fi* and *Logs & Console*. Opening the port did not reset the board.
3. *Change Wi-Fi*: the user picked the home network and typed its password in the dialog (it went
   from the browser to the board only); the board joined and the dialog offered *Visit Device*.
4. *Update GBS Reimagined*: written over USB, then *Installation complete!*; after *Next* the dialog
   found the board over Improv again and showed it.

**How soon the board answers after a reset** (three runs each, `reboot` on the console, timed from
its reply):

| What | Time |
|---|---|
| the console answers (main loop running, after the 1.5 s splash) | 2.44, 2.45, 2.45 s |
| the saved network joined | 7.69, 7.72, 7.72 s |
| first Improv state, asked every second as the installer does | 7.69, 7.72, 7.72 s (`provisioned`) |

The join took 5.3 s after the loop started in all three runs. With a saved network the board
holds the state until the join is settled, or 8 s after it first read the question, so by design
it answers within about 10.5 s of a reset (2.45 s + 8 s; calculated, not measured). With no network
saved (a board just erased) it answers as soon as the loop runs, about 2.5 s. The manifests ask
the installer to wait 20 s after flashing (`new_install_improv_wait_time`; 10 s by default in ESP
Web Tools 10.4.0).

## 2026-10-15 — M3 gate: a blank board installed from the browser, following only the guide

**Method.**
- Before: the whole flash backed up (`backups/20261015-104456-ec64c9d4eac4.flash.bin`), and the
  settings, levels and profiles saved from the board's `/api/backup`.
- The whole flash erased (`esptool erase-flash`). Three regions read back afterwards (0x000000,
  0x300000, 0x3FB000, 16 KB each) were all 0xFF.
- The installer served locally with this branch's build (`0.1.0-dev`, image sha256 `8c1fb225…`,
  `installer_site.py --build`, `pnpm -C installer serve`).
- The owner followed only `docs/user-guide/pt-BR/README.md`, "Instalando pelo navegador", in Chrome.
  The one difference from the guide: `http://localhost:4173` instead of the public address, which
  exists from the first release.

**Result: passed.** Every step worked as the guide describes:
- the install with "Erase device";
- the Wi-Fi form, where the owner gave the network and password in the dialog;
- the picture on the TV.

Afterwards, on the board:

| Check | Result |
|---|---|
| status | `scaling`, NTSC 15 kHz (240p/480i) on RGB, composite sync, 260 lines, program `ntsc-960p` (output Auto: 1280x960), sync quality 100 % |
| Wi-Fi | joined, address 10.0.0.119, from the credentials given over Improv |
| capture (HD60, 30 frames) | picture: mean luma 49.9, 41.5 % lit; the game shown whole and clean (`bench-runs/20261015-105437-m3-gate-blank-install/frame_016.png`) |

**Owner's remark.** The installer's own dialog (ESP Web Tools) stays in English when the page is in
Portuguese. ESP Web Tools 10.4.0 has no translations: its texts are fixed in its code, and upstream
says it does not support them (esphome/esp-web-tools#407; #506 is open). The guide and the page
already gloss the dialog's English labels in pt-BR.

**Afterwards.** The saved settings, levels and profiles 1–3 were put back the way the web page
restores a backup; the output resolution (1080p) was confirmed with *Keep*.

## 2026-10-15 — Release 1.0.0 and the public installer site

**The release** (`v1.0.0`, built by the release workflow):
- Three assets: `gbs-reimagined-v1.0.0-gbsc.bin` (574 592 B), `gbs-reimagined-v1.0.0-gbsc.ota.bin.gz`
  (394 476 B) and `SHA256SUMS`.
- Downloaded into an empty folder, both files match `SHA256SUMS`.
- The update file's header reads `gbsr board=gbsc version=1.0.0`, and it decompresses to the image
  byte for byte.

**On the board:**
- The release's update file was sent to `/api/update` and answered `{"ok":true,"version":"1.0.0"}`
  after 4.19 s.
- The board came back `scaling`, at 1080p with frame lock, with the owner's settings and profile 3
  active.
- Over Improv it reports `GBS Reimagined 1.0.0`.

**The site** (`https://alexmtos.github.io/gbs-reimagined/`, published by the *pages* workflow after
the repository was made public and Pages set to deploy from GitHub Actions):
- `manifest.json` names 1.0.0.
- `latest.json` names 1.0.0 with the release notes link. It is served with
  `Access-Control-Allow-Origin: *`.
- The update file it points to matches its SHA-256 and size.
- The site's image is identical to the release asset.

**From the board's page**, *System*, *Firmware update*, *Check for updates* (the owner, in Chrome):
"Esta é a versão mais recente." The page read the public `latest.json` and found nothing newer than
1.0.0.
